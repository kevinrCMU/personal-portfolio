Self-taught project · Go + APIs

Precipitation
Forecast

Go · net/http · JSON · HTML templates · REST APIs

What I built

I built a small Go web app that estimates the user’s location, gets the correct forecast from the National Weather Service, and displays the chance of precipitation for upcoming forecast periods.

Why I made it

I mostly wanted an excuse to learn how to use APIs. I started with a simple weather idea and choosing go because its a very convienent option for this kind of project. Working with go was the part I enjoyed most.

What I learned

The project gave me hands-on experience making HTTP requests in Go, decoding JSON into structs, handling nullable API values, using request timeouts, and rendering server-side HTML templates.

A problem I had to solve

The weather API does not take an IP address and immediately return a forecast. I had to get coordinates first, use those coordinates to find the correct NWS forecast endpoint, and then make another request for the actual forecast data.

From main.go

Chaining the API requests

Each request gives the app the information it needs for the next one. Keeping those steps in separate functions made the process much easier for me to understand and debug. 

// location → NWS endpoint → forecast

lat, lon, err := getLatLon(ctx)
if err != nil {
    return nil, err
}

forecastURL, err := getForecastURL(ctx, lat, lon)
if err != nil {
    return nil, err
}

fr, err := getForecast(ctx, forecastURL)
if err != nil {
    return nil, err
}

Information Systems · Team project

MenuCheck

HTML · CSS · JavaScript · Systems analysis · Communication

The project

MenuCheck was a four person Information Systems project where we had to identify a real organizational problem and propose a technology based solution. We were not building the full application. Our job was to design the system and explain how it would actually work.

What I worked on

I designed and built the website used to present our proposal. My teammates focused on other parts of the project, so I had to understand their research and ideas well enough to turn them into one clear site instead of four disconnected pieces of work.

What I learned

This was one of the projects that made Information Systems make more sense to me. We had to think beyond whether the technology could work and consider the people using it, different stakeholders, adoption, business value, and possible downsides.

The challenge

There was a lot of research and analysis to communicate. My challenge was turning that material into a website that was easier to follow than a long report. I used clear sections, diagrams, a product mockup, and a consistent visual style to organize the group's work.

Solo web development project

MonoMuse

HTML · CSS · JavaScript · jQuery · Leaflet

What I built

I designed and built a multi page museum website with exhibition pages, ticket purchasing, checkout, form validation, an image gallery, responsive navigation, and an interactive Leaflet map.

What I practiced

The project let me apply HTML, CSS, and JavaScript to a complete site instead of isolated exercises. I also had to learn how to work with jQuery and Leaflet alongside my own JavaScript.

The challenge

As I added more pages, I had to keep the design and navigation consistent across the whole site. I also worked on making the steps from viewing exhibits to buying tickets and checking out easy to follow.

What I took from it

It was a good step from making individual web pages to thinking about how a real user would use the site. I became more comfortable debugging interactions and connecting different pieces of a site together.
